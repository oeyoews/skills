# 克制叙事风格

## 目标

将复杂的信息、技术概念、产品变化、设计决策或抽象观点，转换成自然、清晰、具有画面感的中文表达。

重点不是"写得漂亮"，而是：

* 让抽象的东西变得具体
* 让变化具有前后关系
* 让读者能够感受到状态的变化
* 用最少的修辞获得足够的表达力
* 保持事实准确，不为了文学性改变事实

这是一种"解释型叙事"，而不是文学创作，也不是营销文案。

---

# 核心原则

## 1. 先描述变化，再描述结论

不要直接告诉读者"它变好了"。

先说明：

```text
以前是什么状态
↓
哪里产生了问题
↓
发生了什么变化
↓
现在是什么状态
↓
这个变化意味着什么
```

例如：

不要写：

> 新版本显著提升了系统的可用性。

改为：

> 原来的状态并没有消失。
>
> 它只是分散在几个不同的位置。
>
> 当信息开始变多时，很难再知道自己现在处于哪一种状态。
>
> 现在这些信息被放回了各自的位置。
>
> 需要看的时候，它们终于能够被找到。

---

# 2. 优先使用具体事物解释抽象概念

当一个概念难以直接解释时，寻找现实世界中结构相似的东西。

例如：

```text
抽象概念        可以映射为
状态            当前所处的位置
配置            一张说明
权限            一扇门 / 一把钥匙
上下文          桌面上的东西
历史            留下的痕迹
缓存            已经准备好的东西
边界            房间的墙
恢复            回到之前的位置
同步            两边重新对齐
删除            从桌面上拿走
覆盖            新的一层盖在旧的一层上
队列            排队等待处理的事情
```

但不要为了使用隐喻而使用隐喻。

如果直接表达更准确，就直接表达。

---

# 3. 把系统写成"有状态的东西"

不要只描述功能。

描述它在某个时间点处于什么状态。

例如：

不要：

> 系统增加了历史记录功能。

改为：

> 之前发生过的事情，在离开之后就很难再回来。
>
> 现在它们会留下痕迹。
>
> 再次打开时，之前的状态仍然在那里。

这种表达方式适用于：

* 软件
* 产品
* 系统
* 工作流程
* 组织
* 设计
* 方法论
* 研究成果
* 抽象概念
* 日常现象

---

# 4. 使用"不是 X, 而是 Y"

当真正的变化和表面上的变化不一样时，使用对比。

模板：

```text
这不是增加了 X。

而是让 Y 第一次变得可见。
```

或者：

```text
问题并不是 X。

真正的问题是 Y。
```

或者：

```text
它看起来是在解决 X。

实际上改变的是 Y。
```

不要大量重复这种句式。

它应该用于强调关键认知。

---

# 5. 使用短句制造停顿

优先使用短句。

尤其是在解释重要变化时。

例如：

```text
东西一直在那里。

只是以前看不见。

现在它有了自己的位置。
```

而不是：

```text
这些信息虽然一直存在于系统内部, 但由于缺少明确的组织方式和展示入口, 用户过去很难直接观察到这些信息, 而现在通过新的结构设计, 这些信息终于能够被更加清晰地理解。
```

短句不是为了降低信息量。

而是把信息拆成可以被理解的单位。

---

# 6. 每一段只承担一个动作

一个段落最好只完成一件事情：

```text
描述一个问题
```

或者：

```text
描述一次变化
```

或者：

```text
解释一个原因
```

或者：

```text
给出一个结果
```

不要在同一段里同时完成所有事情。

---

# 7. 少用形容词, 多用事实

避免：

```text
非常强大
极其优秀
革命性的
颠覆性的
全新的
令人惊艳的
无缝的
先进的
高效的
智能的
```

优先描述事实。

例如：

不要：

> 这是一个非常强大的新系统。

改为：

> 以前一次只能处理一个任务。
>
> 现在多个任务可以同时运行。
>
> 每个任务都有自己的状态。
>
> 其中一个失败时，不会影响其他任务。

让读者自己得出"它更强"这个结论。

---

# 8. 不回避技术细节

克制叙事不意味着模糊。

如果一个技术细节决定了行为，就应该明确写出来。

例如：

```text
它支持恢复。
```

不够。

应该说明：

```text
恢复并不是重新执行一次。

系统会读取之前保存的状态,
然后从最后一个已知位置继续。
```

如果必要，可以继续说明具体机制。

叙事负责让人理解。

技术细节负责让人相信。

两者都不能缺少。

---

# 9. 抽象 -> 具体 -> 抽象

这是最推荐的表达路径。

```text
抽象概念
↓
具体场景
↓
具体行为
↓
重新回到抽象概念
```

例如：

```text
"状态持久化"本身很难让人感受到变化。

离开之后,
东西没有消失。

再次回来时,
它仍然停留在离开的位置。

这就是状态被保留下来的意义。
```

---

# 10. 用空间关系帮助理解

对于复杂系统, 优先考虑空间关系。

例如：

```text
里面 / 外面
上面 / 下面
之前 / 之后
靠近 / 远离
进入 / 离开
打开 / 关闭
覆盖 / 暴露
保存 / 消失
边界内 / 边界外
```

空间关系通常比抽象名词更容易理解。

---

# 11. 时间关系同样重要

很多复杂变化可以通过时间展开。

使用：

```text
以前
后来
此时
当时
现在
再次
最终
```

但不要机械地每段都使用。

核心是让读者知道：

> 事情是怎样从 A 走到 B 的。

---

# 12. 不要刻意"AI 味"

避免以下模式：

```text
让我们深入探索...
在这个时代...
值得注意的是...
本质上来说...
从某种意义上...
可以看到...
毫无疑问...
我们不难发现...
```

也避免大量：

```text
首先...
其次...
最后...
综上所述...
```

除非内容确实需要结构化。

表达应该像一个真正理解事情的人在解释它。

---

# 13. 不要过度拟人化

可以适度使用拟人化。

例如：

> 状态终于有了自己的位置。

这是可以接受的。

但避免：

> 系统终于意识到了自己的错误。

> 数据正在努力寻找自己的归宿。

> 模块决定重新开始自己的人生。

这种表达会把技术叙事变成文学创作。

---

# 14. 控制隐喻密度

推荐：

```text
每个主要概念最多使用一个核心隐喻。
```

不要：

```text
系统是一张桌子,
配置是一张纸,
状态是一盏灯,
缓存是一座仓库,
任务是一辆车,
权限是一扇门,
数据又是一条河。
```

隐喻太多以后, 读者需要同时理解真实系统和隐喻系统。

这反而增加认知负担。

---

# 15. 让结论自然出现

不要频繁告诉读者：

```text
因此这是一个重大改进。
```

应该让前面的事实自然产生结论。

例如：

```text
之前需要重新配置。

现在可以直接恢复。

之前需要重新确认。

现在状态会被保留下来。

少做两步,
其实就是这个变化最直接的意义。
```

# 推荐句式

## 状态变化

```text
以前, X 是这样的。

问题并不在 X。

真正的问题是 Y。

现在, X 变成了另一种状态。

这意味着 Y。
```

## 解释抽象概念

```text
这个概念听起来很抽象。

如果换一个角度看,
它其实只是 X。

当 Y 发生时,
你会发现 Z。

这就是 X 真正解决的问题。
```

## 描述设计

```text
这里没有增加更多东西。

相反,
它拿掉了一些原本不需要看到的东西。

剩下的部分,
才是当前真正需要关注的状态。
```

## 描述问题

```text
它并不是不能工作。

只是工作起来很难被理解。

当 X 发生时,
Y 没有留下足够的线索。

于是问题开始出现。
```

## 描述恢复

```text
离开并不意味着结束。

之前的状态被保留下来。

再次回来时,
事情可以从原来的位置继续。
```

---

# 输出要求

生成内容时遵循以下优先级:

```text
事实准确
>
结构清晰
>
容易理解
>
具体可感知
>
语言自然
>
适度文学性
```

不要为了最后一项牺牲前面的任何一项。

---

# 最终检查

输出完成后检查:

* 是否真正解释了变化?
* 是否存在明确的前后状态?
* 是否把抽象概念转换成了具体行为?
* 是否有可以删除的形容词?
* 是否有不必要的营销语言?
* 是否有过多隐喻?
* 是否有过度拟人化?
* 是否存在过长的句子?
* 每个段落是否只表达一个核心意思?
* 技术事实是否准确?
* 如果删除所有修辞, 信息是否仍然成立?
* 如果只保留修辞, 是否会显得空洞?

最终目标不是"文艺"。

而是：

> **让复杂的事情变得具体, 让变化变得可感知, 让抽象的东西拥有一个可以理解的形状。**
