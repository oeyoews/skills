# 周报生成

从仓库活动与用户补充信息生成结构化周报. 默认面向研发场景, 输出简体中文, 标点用西文 `,` `.` `;` `:`.

## 触发与输入

用户可能只说一句「写周报」. 先确认或推断:

| 项 | 默认 | 如何调整 |
|---|---|---|
| 周期 | 上周六 00:00 ~ 本周六 24:00 (本地) | 用户给出日期范围时以其为准 |
| 范围 | 当前仓库 + 用户口述的其他工作 | 多仓库时逐个收集或请用户列举 |
| 受众 | 微信群聊 / 项目组 | 语气偏正式时可加重书面感 |
| 文风 | 专业书面, 自然简洁 | 用户要求口语/极简时可更短 |
| 格式 | 纯文本编号列表 `1. xxx` | 用户要求邮件/文档时改排版, 不改事实 |
| 落盘 | `weekly/<本周六YYYYMMDD>/index.md` | 用户指定路径时以其为准 |

缺省周期: **上周六到本周六** (含首尾, 本地时区). 按下列规则算日期, 再写入 `git log --since` / `--until`:

1. **本周六**: 当前日期所在自然周 (周一至周日) 的周六.
   - 周日算作同一周的周六为昨天; 周一至周五为本周未到/已过的周六; 周六为当天.
2. **上周六**: 本周六往前 7 天.
3. **git 范围**: `--since="<上周六 YYYY-MM-DD>"` (当天 00:00), `--until="<本周六+1天 YYYY-MM-DD>"` (`--until` 为开区间, 故 +1 天以包含本周六全天).

示例 (今天 2026-08-29 周六): 上周六 2026-08-22, 本周六 2026-08-29, `--since=2026-08-22 --until=2026-08-30`.

## 工作流

按序执行, 不要跳过证据收集:

```
任务进度:
- [ ] 1. 确定周期与受众
- [ ] 2. 收集 git / PR 证据
- [ ] 3. 合并用户口述与对话上下文
- [ ] 4. 归类、去重、写周报
- [ ] 5. 写入 weekly/<YYYYMMDD>/index.md
- [ ] 6. 自检 (见文末清单)
```

### 1. 收集 git 证据

在目标仓库根目录并行或顺序执行:

```bash
# 提交概览 (作者、日期、标题)
git log --since="<上周六>" --until="<本周六+1天>" --pretty=format:"%h %ad %an %s" --date=short

# 按作者统计提交数 (多人协作时)
git shortlog -sn --since="<上周六>" --until="<本周六+1天>"

# 变更文件规模 (辅助判断「大项」)
git log --since="<上周六>" --numstat --pretty=format:"COMMIT:%h %s" --no-merges
```

解读原则:

- **按主题合并 commit**, 不要逐条罗列 `fix typo`.
- **Merge commit** 通常代表已合并的 PR/分支, 优先归纳为功能交付而非列 SHA.
- **revert / WIP** 单独标注, 不粉饰为成果.

### 2. 收集 PR / Issue (可选)

若已安装 `gh` 且仓库在 GitHub:

```bash
gh pr list --state merged --search "merged:>=<上周六>" --limit 50
gh issue list --state closed --search "closed:>=<上周六>" --limit 30
```

无 `gh` 或权限不足时, 仅用 git log, 并向用户说明 PR 列表未纳入.

### 3. 合并上下文

除 git 外, 纳入用户明确提到的内容:

- 会议、评审、联调、线上值班、客户沟通
- 未提交代码的调研、文档、设计

**不要编造** 未在证据或用户输入中出现的工作项. **不写** 下周计划、风险、待协调 (用户未明确要求时).

### 4. 归类写法

将事项归入下列类别 (无内容则省略该节, 不写「无」):

| 类别 | 写什么 |
|---|---|
| 需求/功能 | 交付或推进中的产品能力, 对应模块名 |
| 缺陷修复 | 线上/测试问题, 影响范围 |
| 技术建设 | 重构、性能、工具链、CI、依赖升级 |
| 协作支持 | Code Review, 答疑, 文档, 分享 |
| 调研学习 | 预研结论与后续计划 |

每条用 **结果导向** 表述: 做了什么 + 达成什么 / 当前状态. 避免空泛「继续优化」「跟进中」而无对象.

## 输出格式 (默认: 微信群聊, 仅本周工作)

正文为编号列表, 只写本周已完成或实质推进的工作, 不写下周计划、风险、待协调.

**回复与落盘均用 fenced code block (`text`) 包裹正文**, 便于一键复制发微信. 首行固定 `本周周报:`, 其后接编号列表. 不用 Markdown 标题 (`#`)、不用其他分段标签、不用表格、不用 `-` 列表.

```text
本周周报:
1. 完成聊天停止生成功能, 前后端联调通过并已合入
2. 修复 Windows 11 托盘图标不显示问题, 打包验证通过
3. 拆分 base-model-id 模块, 解决客户端 bundle 误依赖服务端模块的问题
```

`index.md` 文件内容与回复 code block 一致: 外层 ` ```text ` + 正文 + 闭合 ` ``` `, 无额外 Markdown 包裹.

### 文风: 专业书面

像工程师正常写周报: **说清楚做了什么、结果如何**, 语气正式但不「表演专业」.

**推荐**:

- 动词用常见书面语: 完成、修复、优化、参与、评审、解决、验证通过、已合入
- 一条一事, 带必要技术名词 (模块、API、平台), 不贴 commit 原文
- 结果写清楚: 已合入、联调通过、问题已修复、评审完成

**少用或不用** (显得刻意、一眼「话术」):

推进、落地、闭环、对齐、夯实、沉淀、赋能、抓手、专项、全链路、保障 XX 体验、支撑 XX 业务

**也避免**:

- 空话: 「持续推进」「各项工作有序开展」
- 过于干瘪: `fix tray icon` 式 commit 流水账
- 一条堆多个大词或超过一句能说完仍硬凑

### 写法规则

- **每条一行**, 编号后直接写完整句, 句号结尾.
- **按主题合并**, 一条对应一件可汇报的事, 不逐条列 commit.
- **3~8 条** 为宜, 无内容时不输出占位 (不写「无」).
- **首行** 固定 `本周周报:` (西文冒号), 换行后接 `1. 2. 3.`
- 不加其他总标题 unless 用户明确要求替换抬头
- 避免 hash/PR 号 unless 用户需要追溯.
- 编号用阿拉伯数字 + 英文句点 `1.` `2.`, 不用 `①` 或 emoji 列表.

### 变体 (仅用户明确要求时)

用户单独要求「下周计划」「待协调」「风险」时, 可在编号列表后追加对应段落, 仍用 `1. 2. 3.` 格式.

## 落盘路径

生成正文后**必须写入文件**, 并在回复中用 **fenced code block** 展示相同内容 (便于复制).

| 项 | 规则 |
|---|---|
| 根目录 | 仓库根 `weekly/` (不存在则创建) |
| 子目录 | `weekly/<本周六YYYYMMDD>/`, 如 `weekly/20260829/` |
| 文件名 | `index.md` |
| 完整路径示例 | `weekly/20260829/index.md` |
| 文件内容 | ` ```text ` 围栏 + 编号列表正文 + 闭合围栏 |
| 编码 | UTF-8, 换行 LF |
| 覆盖 | 同周期再次生成时覆盖 `index.md`, 不追加版本后缀 |

目录名用**本周六**的 `YYYYMMDD`, 与默认统计周期结束日一致.

```bash
# 示例: 本周六 2026-08-29
mkdir -p weekly/20260829
# 写入 weekly/20260829/index.md (含 ```text 围栏)
```

回复用户时: 先写文件路径, 再用 fenced code block 贴出与文件相同全文 (勿省略围栏).

## 自检清单

交付前核对:

- [ ] 周期与 git `--since` / `--until` 一致
- [ ] 无虚构事项; 口述与 git 已对齐
- [ ] 同类 commit 已合并叙述, 非流水账
- [ ] 仅本周工作, 无下周/待协调 unless 用户要求
- [ ] 首行为 `本周周报:`, 其后为编号列表
- [ ] 文风专业自然, 无显眼黑话与空话
- [ ] 中文标点为西文符号
- [ ] 已写入 `weekly/<YYYYMMDD>/index.md`
- [ ] 目录名 YYYYMMDD 与本周六日期一致
- [ ] 敏感信息 (密钥、内部账号、未公开客户名) 已剔除或泛化
